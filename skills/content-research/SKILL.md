## 生产流程（与 cron job prompt 对齐，9 步）

1. **读素材** `cat /tmp/all_deduped.json`（预采集已完成，正常 ≥30 条、≥3 源）
2. **跨日去重**：读昨日 `content-research-{昨日}.md`，已覆盖话题不重复
3. **GitHub 推荐**：只从 `/tmp/gh_fresh_candidates.json` 里各赛道的 `fresh` 列表选（每赛道 1 个）——
   搜索、历史推荐去重、跨赛道去重**全部已在 `scripts/gh_recommend_candidates.py` 内完成**；
   🔴 **禁止自选仓库/凭印象推荐**（2026-10-10 事故：gh 查询拼错 → 候选天天为空 → agent 凭印象推荐 → 同一项目连推 3–4 天）
4. **生成完整版**（≤2500 CJK 字）→ 写入当天文件
5. **IMA 笔记同步**（强制）：`python3 ~/.hermes/skills/digital-twin/content-research/scripts/ima_sync.py $(date +%Y-%m-%d)`
   - 脚本**已幂等**：按「M月D日」检索（笔记实际标题来自报告 H1「每日内容研究简报 · M月D日」；**不要拿「📋每日简报 · …」去搜——搜不到当天笔记就会重复导入**），已存在则输出 `SKIP note_id=...`（正常，别重复导入）。`--force` 可强制重导。
   - ⚠️ **重复笔记 IMA OpenAPI 删不掉**（只有 search/list/get/import/append，无 delete）→ 同日出现多篇必须请用户在 IMA 客户端手动删旧篇；重同步前先确认幂等是否命中，别先手动 `--force`。
6. **飞书 GitHub 入库**（强制）：`SYNC_DATE=$(date +%Y-%m-%d) python3 ~/.hermes/scripts/sync_gh_repos.py`
   - 写库前会过 `sanitize_desc()`：乱码/词语粘连/繁体异体一律置空并记日志，不让脏文本进对外表
7. **统一校验（硬门禁）**：`python3 ~/.hermes/scripts/daily_briefing_check.py $(date +%Y-%m-%d)`
   - 单一数据源（2026-09-16 合并）：完整性（IMA / 飞书入库 / 去重）+ 格式（链接 / 引用 / 结构 / 共识分歧格式 / 分行 / 字数 / 版本串 / 文本卫生）**一个脚本全查**
   - exit 0 → 通过；exit 1 → 逐条修正报告后重跑（最多 2 轮）；2 轮仍不过 → 微信摘要末尾必须追加一行 `⚠️ 校验：...`，**不许静默吞掉**
   - 结果同时写机读凭据 `/tmp/daily_briefing_check_YYYY-MM-DD.json`
   - 独立执行层：cron `09db67dfb6d9`（内容日报校验看门狗，每天 06:45）会再跑一次，失败才推微信
8. **微信摘要版** = 最终回复（≤600 字）
9. **结构化 JSON（数据层，D6-1）**：`python3 ~/.hermes/scripts/briefing_to_json.py $(date +%Y-%m-%d)`
   - 产物 `~/hermes-output/content-research/data/YYYY-MM-DD.json`；schema `schemas/briefing.schema.json`（要点恰 3 条 / 3 赛道各含 news·insights·actions / GitHub ≥3）
   - 只放元数据/结论/链接，**不存正文**——静态站与自动上站（D7/D8）只消费该 JSON
   - exit 0=通过 / 1=报告缺失 / 2=自检未过（要点条数、赛道结构、GitHub 数）；兼容完整版与摘要版两种报告形态
   - 细节见 （采集流水线细节（含运行时调度），公开版未包含） 步骤 9.5

采集侧的完整细节（RSS 分组拉取、Tavily 补漏、Web Scraping、RSSHub、跨层去重、热点雷达、IT之家过滤）见 （采集流水线细节（含运行时调度），公开版未包含）。

## 🔴 输出格式铁律（权威定义）

**结构（微信摘要版）**
```
📋 今日简报 · M月D日
🎯 今天要点（3条 • ，每条 ≤45 字，无括号）
🤖 AI产业技术（📌1句 + 🔍1句 + 💡1句）
💼 企业AI应用（📌1句 + 🔍1句 + 💡1句）
🎨 内容创作（📌1句 + 🔍1句 + 💡1句）
⭐ GitHub推荐（项目名 + ⭐精确星数 + 1句话）
📊 共识与分歧（**🔵 共识解读** / **🔴 分歧解读**，各1句，禁止具名）
```

**硬规则（实测踩坑总结）**
- 🔴 **空行铁律（微信渲染）**：微信把「单换行」合并成一行，所以摘要里**任意两个非空行之间必须有一个空行**——段标题（`📋/🎯/🤖/💼/🎨/⭐/📊`）、每个 `•`、每个 `●`、同赛道 `📌/🔍/💡`、`**🔵 共识解读**`/`**🔴 分歧解读**` 全都算。**最常漏的是 📌/🔍/💡 与 ● 之间**（2026-09-20 整篇挤成一坨，用户直接报障）。已由 `daily_briefing_check.py` E13 逐行硬拦
- 🔴 **GitHub 推荐恰好 3 个**（完整版与摘要版同一批，每个赛道 1 个、不重复）：**多推一个同样判违规**（2026-09-20 实推 5 个）。旧校验器只拦「<3」，导致多推放行 → 已升级为「≠3 即 error」（完整版 E9b / 摘要 E12）
- 🔴 **要点段铁律**：`🎯` 要点**恰好 3 条**（完整版用 `1.`、摘要版用 `•`，**禁止 `• 2.` 混排**）；**禁止把采集/筛选过程写进正文**（「未记载于采集」「此条为非 AI 素材不展开」「未采用」这类排除说明一律不许出现——非 AI 素材的正确处置是**静默丢弃**）；**完整版与摘要版的要点必须是同一批事件**（曾出现摘要版 3 条正确、完整版只剩 2 条且混入非 AI 条目）。已由 `daily_briefing_check.py` 硬拦，原文见 `references/output-specs.md`
- 赛道顺序固定 **🤖 → 💼 → 🎨**
- 共识/分歧用**正文加粗** `**🔵 共识解读**`，**禁止**写成 `## / ###` 标题
- 🔴 **「禁止具名」要按机械判据复核，不能只看校验器绿了**：`daily_briefing_check.py` 的具名拦截实现是**硬编码实体清单**（`BANNED_IN_CONSENSUS`）——清单里列过的品牌/数字才拦得住，清单外的（新出现的厂商名、`3万`、`Bedrock` 这类）照样通过、还报「✅ 全部通过」。所以：① 结论段/分歧段一旦出现**大写英文词、百分号、阿拉伯数字**即判人工复核；② 每次具名事故都要把新实体追加进清单，周期性把清单升级成正则；③ **改硬门禁后必须拿一条已知违规样本喂给它**（把最近那次事故的原文放进去跑一次），**看到它真的报错**，才能在文档或对外文章里写「已由脚本硬拦」
- 🔴 **校验规则要封堵「成对短路」的绕过路径**：任何「成对/数量」类校验，只要「数量为 0」被判合法，就等于给整段开了免检通道（实测：推荐阅读段 0 条 📝 时主判定与成对检查双双短路，条目写成「• 标题（来源）正文…URL」可以完全静默通过）。两条固定修法：① **把「该段 0 条」单列为 error**（不是等成对检查顺带抓）；② **URL 检查不能只抓「整行裸链」**，必须放宽为「行内出现未包裹进 `]( )` 的 URL 片段」（`](` 前豁免，`📝/💡` 行整体豁免）。改完必须拿真实修复版回跑确认零误报 + 合成反例确认命中（边界样本：URL 后跟中文全角括号来源、URL 落在理由文本行内）。
- 🔴 **落地项/洞察项行首禁 emoji，但文字前缀保留**：「弱信号：」这类前缀有信息量 → 保留文字、去掉 emoji；🟡 等 emoji 前缀禁用（同一符号在摘要规范里本就被禁）。结构标记 🏷️📌🔍💡📝⭐ 豁免。由 `daily_briefing_check.py` E15 报 warn。⚠️ 统计这类口径漂移必须**全量扫语料**：抽样只看到 8 处，全量实为 24 天 / 67 处，据此定工作量会差一个量级。
- 版本号格式：`*生成：YYYY-MM-DD · 三赛道 v8.4.2*`（不得回落 v8.0/v8.3.0/v8.3.1/v8.4.0/v8.4.1）
  - 🔴 2026-09-16 统一：此前规则写 v8.3.1，而 skill 本体已是 8.4.x（结构性调整升次版本），
    三处口径（本文件 / cron prompt / 日报页脚）不一致 → 现统一为 **v8.4.2**，
    由 `daily_briefing_check.py` 校验（不等则告警）
  - 🔴 2026-09-20 升 v8.4.2：摘要新增「空行铁律」与「GitHub 恰好 3 个」两条硬校验（E9b/E12/E13），
    prompt 与三处文档同步；改版本号时**必须同时改这四处**：本文件 / cron prompt / 校验器 `EXPECTED_VERSION` / references
- GitHub 星数必须 **GH_TOKEN + API 精确获取**，禁止写约数或编造
- 完整版 ≤2500 CJK 字；微信摘要版 ≤600 字
- 引用事件格式 `▸ 引用N：` 且单独分行

完整版结构、共识/分歧长文规范、质量速查表见 `references/output-specs.md`；微信排版细则见 `references/wechat-summary-format.md`、`references/output-template.md`。

## GitHub 开源趋势（L1.5，每日执行）

- **通道 0（优先）**：`sort=stars` 取 top 级大项目（star ≥ 10K，不限创建时间）
- **通道 1（兜底）**：近 180 天新项目（500–10K 星）补位
- 🔴 **每天至少推荐 1 个**，禁止输出"今日无新达标项目"
- 🔴 去重：按 `fullName` 大小写不敏感比对「历史库 + 当日」，否则会重复推荐。
  **2026-10-10 起由 `gh_recommend_candidates.py` 确定性执行**（历史库 `recommended-repos.json` + 近 30 天本地报告取并集，再跨赛道去重），agent 只做「从 fresh 列表挑 + 写 📝/💡」
- 🔴 命中 API 限流（403）或通道失败时，**必须在简报里注明原因**，不能静默跳过
- 取星数：`GH_TOKEN` + GitHub API（`api.github.com`）；API 不可达时的兜底见 `references/github-stars-shields-fallback.md`
- 排错：`references/github-troubleshooting.md`、`references/github-dedup-chain-pitfall.md`；写库规则 `references/github-write-rules.md`

## 去重与防漂移（P0 门）

1. **跨日去重**：昨日报告已覆盖的话题今日不重复
2. **历史推荐去重**：GitHub 推荐不得是历史已推过的项目 —— 由 `gh_recommend_candidates.py` 在预采集里排除，并由校验器 **E9c 硬拦**（报告里的项目 ∈ 今天之前的历史 = error，2026-10-10 新增）
3. **单日内交叉去重**：同一项目在多通道命中只留一条（预采集里连跨赛道也去重了）
4. 防漂移规则模式（把"必须执行"写成可验证的规则，而不是靠记忆）与单一数据源原则见 `references/engineering-patterns.md`

## 失败模式与 fallback（都是实测踩过的）

| 失败 | 现象 | 处置 |
|---|---|---|
| **GitHub API 不可达** | `api.github.com` TLS 超时（2026-09-16 实测 VPS 网络层全断） | 用 shields 徽章兜底取星数；若仍失败，简报中注明"星数为徽章口径/取数失败"，**不得编造** |
| 旧报告阻塞采集 | 当天文件已存在 → 只出摘要、不采集 | 手动测试前先删除当天文件（链式故障根因） |
| IMA 同步被跳过 | 用户事后才发现笔记缺失 | 步骤 5 强制 + 步骤 7 校验兜底 |
| 飞书 GitHub 表为空 | 日报有项目、表里没有 | 步骤 6 强制 + 步骤 7 校验兜底 |
| RSSHub 未启动 | 中文源全空 | 先 `terminal(background=true)` 启 RSSHub 再拉取；**路由超时给到 30s**（热榜/虎嗅响应 160KB~640KB，10s 会被砍成 0 字节文件），失败再补抓一轮 |
| **单源抓取失败静默** | 某源 0 条产出，日志与简报里都不体现（feed 地址失效、被超时砍成 0 字节、429、偶发失败） | 跑 `python3 ~/.hermes/scripts/check_source_health.py` 定位；每日 06:30 有独立告警任务兜底；生成侧按 `references/daily-briefing-rules.md` 第九节披露 —— 判据与三层防护见 `references/source-health.md` |
| 素材陈旧/停更 | 产物时间戳不前移 | 分级告警，见 `references/pitfalls.md` |
| 单源占比过高 | 简报被单一来源刷屏 | 检查信源优先级与配额（`references/consensus-division-rules.md`） |
| 格式漂移 | 共识/分歧写成标题、要点挤一行 | 用 `references/verification-checklist.md` + `scripts/daily-briefing-check.py` 校验 |

## 检查点（手动跑完必查）

1. 当天文件时间戳/大小是新生成的
2. `最大共识与分歧` 段没有出现 `##` / `###` 标题（必须是加粗正文）
3. 引用事件为 `▸ 引用N：` 且单独分行
4. `/tmp/all_deduped.json` 素材 ≥30 条、来源 ≥3 个
5. `daily_briefing_check.py` exit 0（IMA 同步 / 飞书入库 / 去重 / 格式 / 版本串 / 文本卫生）
6. IMA 同日只有 1 篇笔记（重复会让校验器 warning；`ima_sync.py` 已按日期幂等，**但已产生的重复只能人工删**——API 无删除接口，见步骤 5）
7. `data/YYYY-MM-DD.json` 已产出且 `briefing_to_json.py` exit 0（数据层断供会让 D7 静态站空站）
8. **对外发布前（静态站 / 公开仓 / 可分享链接）先过披露边界审计**：扫**全部自由文本字段**（不是只扫被点名的字段）、跑凭据/基础设施/私域工具名扫描、AI 生成内容标识补齐显式+隐式两层；若这轮涉及**口径反转**，额外核对「决策记录 + 站点声明 + 判据」三件配套是否齐备 —— 判据与命令见 `opensource-skill-release` 的「对外公开：落点选择与披露边界」一节，发布闸门细节见本节「静态站发布（D7-1）规范与门禁」

## 静态站发布（D7-1）规范与门禁

站点 = 简报的公开回看入口（日期列表 + 赛道分组 + 共识分歧标注；只放元数据/结论/链接，零后端）。发布前必过下面每条（每条都对应一次实测事故）：

1. **托管落点**：独立公开仓、站点放根目录 —— **已落地（2026-09-20）：仓 `Jennyno1/ai-briefing-site`（公开），站点 https://jennyno1.github.io/ai-briefing-site/**（上线 commit 21cf907e）。技能仓 `Jennyno1/xiaohe-skills` 保持私有；**技能仓保持私有**。前提类断言必须实测：`gh repo view <owner>/<repo> --json visibility`（实测 `Jennyno1/xiaohe-skills` = PRIVATE；私有仓开 Pages 需付费计划，转公开等于曝光全部技能源码与提示词）。
2. **字段白名单与净化对象**（口径已于 2026-09-20 由用户反转，**以本条为准，别再按旧条目删字段**）：白名单**包含 `tracks[].actions`**——「落地行动」公开是用户主动拍板，定位为「主理人工作笔记」，其中出现的选题储备/自我定位等表述属**有意公开**，不是脱敏遗漏。真正要净化的是三类：**私域工具名**（自建 agent 的名字，实测散落在 `github.why` / `reading.reason` / `tracks.insights`）、**内部版本号**（`v8.x`）、**凭据与基础设施路径**。
   - ⚠️ **扫描范围必须是全部自由文本字段**：只扫被点名的那一个字段（如只扫 actions）会整片漏掉 `github.why` / `reading.reason`——评审方一次就抓出 11 处私域工具名，全在我没扫的字段里。
   - ⚠️ **净化一律在生成层做**：`data/*.json` 是公开可下载文件，**前端隐藏不算脱敏**；字段剥离写进构建脚本的白名单，写不进去就等于没做。
   - ⚠️ **口径反转时三件配套缺一不可**：① 决策记录里写明「是用户主动拍板，非遗漏」② 站点/页脚里与旧口径矛盾的声明同步改成诚实表述（旧句「脱敏后发布」会立刻变成假话）③ 扫描范围与豁免判据同步更新。
3. **结论段合规**：共识/分歧的结论段禁具名（规则见 `references/consensus-division-rules.md`）。⚠️ 校验实现是**硬编码黑名单**（`BANNED_IN_CONSENSUS` 17 条），只能挡 08-21 那批反例——实测 2026-09-16~19 四天结论段含「谷歌/Claude Code/MiniMax/Kimi K3/Bedrock/3万」却报「✅ 全部通过」。**黑名单必须升级为数据文件 `brand-lexicon.txt`**（品牌词库命中 OR 数字+单位〔万/倍/%/亿〕；豁免通用术语 AI/Agent/API 与中文序数〔三家/三赛道〕），事故后追加实体，git 历史即审计轨迹。
4. **链接映射走 sidecar**：赛道条目的原文 URL **不进 md**（格式铁律：链接只允许出现在 GitHub推荐/推荐阅读两段，微信渲染与校验器 E5/E6 都依赖它）。补链接 = 生成阶段旁路产出 `links-YYYY-MM-DD.json`（`title → link`），**sidecar 永不进 md**（写死，避免日后塞回正文撞 E6）。素材池 `/tmp/all_deduped.json` 每条都有 `link/source/level`（实测 150/150），标题精确匹配即可，不需爬站反查；历史不回填。
5. **发布闸门**：schema 校验 / 当天 JSON 非空 / 全部链接 `http(s)`（数据侧）+ 前端 `href` 协议白名单（防 `javascript:`）；sidecar 单独校验（link 必须 http(s)、title 与正文条目精确相等、失败率进日志）；**只增量提交**（当天 JSON + manifest），失败不 push、留 pending + 告警；manifest 一致性用集合包含（`manifest ⊆ 实际文件`，空解析日实时计算，不写死数字）。
   - **闸门除了扫关键词，还要断言不变量**（这些是「静默退化」高发区，构建日志全绿也可能已经坏掉）：每天 JSON 必须有 `ai_generated`、不得出现 `version` 字段、`index.html` 必须有显式 AI 标识、页脚占位符（如 `<!--EXCLUDE_NOTE-->`）必须已被替换、页脚不得再出现与现行口径矛盾的旧声明。任一不过 → **exit 1，拒绝发布**。
   - **配置单一来源**：排除日期清单、页脚披露文案、结论段重写映射一律收进 JSON 配置文件（`site_publish_config.json` / `site_consensus_rewrite.json`），脚本只读不抄。实测反例：同一份排除清单被三个发布脚本各写一份，出现「6 天 vs 7 天」不一致，站上缺失的那天没人解释得清。
   - **一次性内容改写走可回滚映射**：结论段这类「只在站点侧改写、原始日报不动」的改动，用 `{date: {field: text}}` 映射文件在构建时套用（保留历史原文，改错直接删映射重建）。
   - **推送执行（推仓）**：`python3 ~/.hermes/scripts/publish_site.py <待推目录> <owner/repo> --branch main --message "..." [--dry-run]`——走 GitHub API 直接建 tree/commit，**不需要本地 clone 或仓**。上线第一步永远先 `--dry-run`，它给出**实际待更新文件清单**（实测常只有 `app.js` / `style.css` 两件，data/ 早已随构建进仓）；再取远程副本逐字节比对确认（`gh api repos/<repo>/contents/data/<f>?ref=main`，base64 解码后比 `size` 与内容）。教训：把「本地已改」当成「线上未生效」会对不上账——数据层修复可能早就进仓，真差的只有前端两件。给协作方对账时附 `md5sum app.js style.css`，它按 hash 终核。⚠️ **对账前先确认对方记录的哈希与当前实际一致**——不一致说明它记录之后产物又进了一轮改动，必须**显式告知实际哈希**，否则它拿错基准终核，结论整份作废。
   - ⚠️ `gh` 走代理会间歇 `EOF`：先 `unset http_proxy https_proxy HTTP_PROXY HTTPS_PROXY ALL_PROXY all_proxy` 再重试 2–3 次。
   - ⚠️ **上线后复扫必须带缓存穿透**：GitHub Pages 是 CDN，`publish` 刚返回就抓线上 `data/*.json` 会拿到**旧副本**（实测 2026-09-20：推送后立刻复扫，最早几天报「有 Hermes 残留 / 缺 ai_generated」，加 `?v=<ts>` 重扫全部为 0 与齐备）。复扫一律带 query 串，否则会把自己吓一跳、甚至误判成闸门有漏洞。
6. **AI 生成标识两层**（《人工智能生成合成内容标识办法》2025-09-01 施行）：**显式**（页脚「内容由 AI 生成并整理」）+ **隐式**（JSON 里 `ai_generated/generator/generated_at`、`index.html` 对应 meta）——两者是并行义务，只做页脚只完成一半。
7. **NOTICE 三段**：内容性质（AI 生成摘要）/ 第三方内容边界（条目为转述、版权归原媒体、侵权即删）/ 联系方式。
8. **防漂移姿势**：站仓放 `gate/`（只放站点侧检查，公开可审计）+ **共享一份 `brand-lexicon.txt`**；简报侧 `daily_briefing_check.py` 留在私有侧，站仓只引用名称与版本，**不复制脚本**（新写一份就多一个漂移源）。
9. **个性化扩展设计（F1，2026-09-20 用户要求，待实现）**：站点从「一份全量视图」演进为「一份数据、按读者关注方向出多视图」，数据始终单源、不做服务端。
   - 落点三件：`site.config.json`（人群画像配置，进仓库可审计）—— `focus_tracks`（赛道子集与排序）/ `action_tags`（给每条 action 打受众标签，如 企业IT / 内容创作 / 个人效率）/ `featured_topics`；schema 只加**可选** `audience` 字段（老数据仍可读）；前端默认全量渲染，`?profile=xxx` 只做**过滤 + 排序 + 高亮**，不追踪、不做服务端。
   - 三步演进：① 赛道显隐 + 排序配置化（零 schema 变更，先可用）→ ② actions 受众标签（要在日报模板里让模型输出标签）→ ③ 多画像多入口。
   - 实现条款写在站仓 `FEATURES.md` 的 F1（站仓=实现契约，本技能=位置与约束），别在两处各写一份设计。

10. **改 UI 前先读 `style.css` 头部的设计语言宪法**（注释就是宪法本体，下一轮的人只读代码，注释与实现必须同步改）：内容至少含 ——
    - **双语义底色**：金底 `note-bg` = 人工行动、蓝底 `--concl-bg` = AI 结论；**各自唯一消费者**（金=落地行动，蓝=`vp-card`），新增用法先回去改条款。条款措辞要用「**金淡底(note-bg)/金标题**=人工行动」，不要写成「≥5% 淡底=人工内容」这类泛指——否则蓝底按字面就违规。
    - **改底色必须整批原子落地**：新底色 token + 旧条款措辞更新 + 冲突容器的中性化（例：`.notice` 原本也在吃蓝 tint 的 `--hover-bg`，不同批中性化则蓝语义底第一天就有两个主人）+ 头部注释同步，拆开做必破「唯一消费者」。
    - 唯一圆角档 `--radius-ctl` 8px（**可交互元素 + 淡底容器**，不是只给交互元素）；间距刻度全部走 `--space-*` token（≤7 档，桌面/移动各一档；**同一元素不许同时用「自身 margin」和「容器 gap」两种间距机制**——那是当年叠加 bug 的遗迹，统一由容器 gap 负责，否则第三个复用点还会再叠一次）；行宽单 token `--measure`；线减法/颜色即信息；带前提的挂起项（写清前提，禁单独决策）。
11. **UI 改动的验收只认「量数」，不认截图**：本地起服务（工作目录里 `python3 -m http.server <port>` 后台跑，访问 `http://127.0.0.1:<port>/`；**别用 `file://`**——页面 `fetch('data/*.json')` 会被浏览器拦掉，量到的是空页），再用浏览器 CDP 量：窄屏 `scrollWidth == clientWidth`（零横向滚动）、目标控件 `rect.right ≤ 视口宽`、触控目标 computed height ≥ 44px（视觉尺寸不想变大就用 `.x::after{content:"";position:absolute;inset:-8px}` 扩热区）、改标签后 computed 字体命中设计值。常见静默坏法（都不报错，只变丑/失效）：① 语义改标签（`h4→h3`）忘同步样式表选择器 → 整条样式作废；② 收敛圆角/颜色 token 时 `@media` 块里的硬编码值把它覆盖回来；③ `var(--不存在)` 静默回退（`border-radius` 变 0、`border-color` 变 `currentColor`）；④ 颜色/泳道按下标映射 → 某项当天缺失即静默前移，改按稳定 key 映射；⑤ document 级方向键无条件 `preventDefault` 抢走正文滚动（只在焦点位于目标容器内时接管）；⑥ 首载用 `pushState` 造出「假历史」（首载 `replaceState`、用户交互才 `push`）。

12. **报告文件名就是站点取材契约**：构建脚本对报告做**严格全名匹配**（`re.fullmatch(r"content-research-(\d{4}-\d{2}-\d{2})\.md")`），衍生命名（`-weixin` / `.v7` / `-summary` / `-重跑`）一律跳过、不会被误用；因此**重跑某天报告必须写回同一个标准名**（覆盖即生效，构建每次全量重建、幂等）。宽松日期提取曾让 `…-2026-08-28.v7.md` 顶掉当天的标准产出（解析为空 → 抹掉当日数据）——严格匹配就是那次事故的修法，**不要改宽**。站点只在每日 07:10 由 `site_autopublish.sh` 重建，**盘中重跑不会自动上站**，要手动补跑构建+发布。详见 `references/daily-briefing-rules.md` 第十节（含一行自检命令）。

⚠️ 同类教训：旧 `scripts/consensus_check.py` 认的是 `## 🔵 共识解读` 标题格式，v8.3.1 迁移成「加粗正文」后它对 09-16~19 一律报「未找到标题」= 全盘假阴性——**格式迁移必须同步升校验脚本**；活着的统一校验是 `~/.hermes/scripts/daily_briefing_check.py`。

### 链接体检：发布前必跑（死链治理）

模型会产出「格式完全正常但打不开」的链接（日期错位 / slug 拼错 / 拿来源站首页占位），静态校验拦不住 → **发布前必跑实测体检**：

- `python3 ~/.hermes/scripts/check_briefing_links.py --report <报告路径>`；exit 1（存在 404 死链）必须换真地址后重跑。已接入 06:45 校验看门狗（全过静默、有死链才推微信）。
- 判定分级：2xx/3xx 放行｜**403/429 = 反爬，放行**（当坏链去「修」是最大误报源）｜404/410 = 死链必须换｜000 = 本机不可达、提示人工确认。
- 🔴 **反爬重的域 404 ≠ 文章不存在**（实测头部科技媒体对机房 IP 的真实文章返回 404）：先搜索确认文章是否存在，再决定改不改；已知反爬域单列降级。
- 链接必须是**文章页**，禁站点首页占位（E13 硬拦）；同一 URL 出现在多期时**全库通改**，只改当期则下期又冒出来。
- 修复路径、分级表与「线上核对假差异」见 `references/link-health.md`。

### DOM 实测的假通过防护（2026-09-21 实测教训）

本地静态服务会被系统回收，**页面加载失败时 DOM 查询一律返回空集**——「0 个引用条目 / 无 vp 区 / 无胶囊」看起来像「已修好」或「本来就没有」，实际是空 DOM 的静默假通过。规则：

1. 起服务后先做健康检查（`urllib.request.urlopen(..., ).status == 200` 或 `curl -o /dev/null -w '%{http_code}'`），再打开页面；
2. **每次读数前先断言关键节点非空**：先取 `document.querySelector('.date-cn').textContent`（或 `#briefing` 子节点数 > 0），为空即判「页面没渲染」并中止本次测量，不要继续读其它 selector；
3. 有缓存嫌疑时给 URL 加 `?v=<timestamp>`；`pkill -f 'http.server'` 会匹配到自己所在命令行、连带杀掉本次命令链——用 `pkill -f '[h]ttp\.server 8899'` 这种不自匹配的写法。

### UI 巡检惯例：透明度是乘法暗坑（2026-09-21 实测）

凡 `opacity < 1` 的**文字**颜色，对比度必须按**混合后实色**算，不能拿 token 原值算——两者能差整整一档：
- 实例：`.footer-note` = `#5d6b80`(ink-3) × `opacity .65` 叠在纸面 `#faf7f2` → 混合实色 `(148,156,168)` → 对比度 **2.59:1**（AA 线 4.5，不达标）；去掉 opacity、用原色 = **5.06:1**（达标）。只看 token 会得出「5.06 没问题」的错误结论。
- 巡检动作：`grep -n "opacity" style.css` 找出所有带透明度的文字节点，逐个算混合实色对背景的对比度；半透明只该用在**装饰元素**（分割线、色点）上。

### 多会话并行时的「落地状态快照」（先验再动）

协作方转来的实施清单描述的**不一定**是当前产物状态：可能已被另一个会话做完，也可能一件没落。**动手前先对目标产物跑一遍状态快照**——对清单里每个待改点 grep 它的标记（token 名 / 注释串 / 选择器 / 函数名），逐项报 ✅/❌ 再动手。实测：一份清单里的 CSS 四件套一件未落，而另一份清单里的 md 三处补丁早已被别的会话完成——照着清单重做 = 重复劳动 + 覆盖别人的改动。

同时：**同一产物有两个写手时按产物类型切分所有权**（CSS 归一个会话、md 归另一个，零交集），约定「原子上线」的批次不得被别的会话拆散实施；**冻结的待推包不得并入新批次**（新批次改动面不同、验收线不同，混在一起没人能对账）。

### 字号/样式普查与计数：归组后再下结论

- **字号普查按 `(computed 值, 标签.类名)` 归组**再判归属：同一个 computed 值可能来自完全不同的机制——UA 默认（`<option>` 13.33px、`<button>` 默认不继承 `font-size` 会落 UA 值）vs 设计刻意。把 UA 默认当设计漂移去「修」，或把设计漂移当 UA 默认放过，都是误判。实例：曾把「13.3px×63」整体归给主题开关，实测 53 个来自 `<option>`（结构性豁免、且多数浏览器不可可靠改），真正缺显式字号的只有 1 个。
- **计数不许用子串 grep 概括**：报错输出里别的消息正文也可能含同一词（实测把「缺链接行」错误里的「…不能只给裸 URL」计成了裸 URL 命中，数目虚高）。要按结构定位（每类错误一行 / JSON 字段）再计数。
- 触控热区类验收要量**可点元素自身**：给容器 `li` 加 padding 不扩大内部 `<a>` 的点击域（实测 li 113px / a 18px 仍点不到）；要么让链接 `display:inline-block` + padding，要么把整行做成链接。

### 渲染层合并类改动的硬约束（2026-09-21）

任何「前端合并/隐藏字段」的改动（例：GitHub 条目的 `note` + `why` 在渲染层合并成一段），必须同时满足：
1. **数据 JSON 的键集合零变化**——合并是展示层的事，绝不反向删数据（引用口径与审计依赖原文）；
2. 自检写成可执行的一行：改动后重建数据，`diff` 新旧 JSON 的键集合（`set(旧) == set(新)`），不等即回滚。

### 裁决转述与上线门禁（多 Agent 协作时的三个坑）

- **转述必做范围锁定**：协作方会把用户的裁决压缩成一句结论，照压缩句改实现会把用户并未推翻的维度一起改掉（实测：裁决只说「A 保留」，我心里推导成「相关扫描范围也缩小」，随手把另一条净化规则撤了，随后被要求改回）。落地前把裁决**拆成维度清单**，逐条列出「这句话动到了哪几条既有规则」；涉及既有规则反转时先问一句。
- **修复类回函自带「可独立复现」证据包**（对方一定会自己跑一遍）：改动前/后两列实测值 + 修改后的脚本本体 + 反例样本 + `md5sum` + 复跑命令，一起发。实测收益：对方拿到后补了本侧没测的两个边界（URL 后跟全角括号来源、URL 落在理由行内），还指出了 harness 的 `utime` 用 `now` 导致历史样本必挂这类环境级坑。只说「已修好」的回函会被打回，也漏掉自己没想到的边界。
- **同一裁决可能有「转述 + 更正」两条**：先到的那条可能不完整——动手前拉一次群消息列表（最近 5–10 条）确认收全；已开工的按最新一条回改，并在回函里点名说「哪一处走偏了、已改回」，比装作没发生可信。
- **「批准照改」≠「批准上线」**：对外动作（推仓库 / 发公众号 / 发公开帖）永远**单列一个待用户点头的问题**。但活儿要干到只剩一个开关——修复集建好、过完闸门、实测值摆在台面上（上线后对方要照这些值复扫）。
- **裁决反转类改动三件配套**（记录 / 声明 / 判据），缺一件下轮评审会当成新事故再提：① 决策记录写明「用户主动拍板，非实现遗漏」② 站点页脚/文档里与旧口径矛盾的声明句同步改成诚实表述③ 扫描范围与豁免判据同步更新（哪条词从硬门禁降为标记）。

## 维护约定

- **单一数据源**：脚本只有一份（`scripts/` 内），不要在多处复制；发现同名不同内容脚本立即合并
- **改规则**：先改 `references/` 原文，再在 SKILL.md 里改指向说明；改完跑一次真机验证
- **版本**：结构性调整升次版本，文案修正升补丁位；版本号同步 cron prompt 与日报页脚
- **归档**：一次性报告、`.bak`、历史快照一律进 `references/archive/`，不留在主目录
- 🔴 **归档保护（2026-09-16）**：**只归档 skill 目录内的文件**；`~/hermes-output/content-research/` 下的历史报告副本（含 `.archive/` 目录内）**一律不要删除或移动**——那里是人工保留的对照基线，曾有运行删掉了当天归档副本，导致无法对账
