# GitHub推荐采集与入库排障

## 按链路定位
1. 读实际日报、候选JSON及采集日志，分别核对数量、星数、创建时间、相关性、赛道和历史去重；进程exit 0不能代替这些验收。
2. 用同一查询做最小真实调用，检查CLI生成的请求参数；结果大量与关键词无关时先查传参，不要先放宽筛选。
3. 审查查询预算与每次淘汰原因，再修改最小范围。采集日志记录query、returned和policy/history/other_track等计数，便于分清没有数据与错误过滤。
4. 改动前备份与校验原文件hash；部署后跑边界样本、真实违规日报及一次真实采集。按实际候选人工核查功能归属，不只信关键词测试通过。
5. 更正正式日报后，分别同步结构化JSON、飞书、IMA与公开站点；逐一验证，未同步的渠道明确保留未完成状态。新增正确记录不自动撤销旧错误推荐，应另外核对旧记录的引用与展示状态。

## 历史网络故障溯源
1. 先定位受影响日期的正式日报和对应cron原始输出，提取采集开始/结束、目标域名、本地代理端口和原始错误；不要拿当前/tmp文件解释历史故障。
2. 用相同时区和窄时间窗读取代理服务日志：`journalctl -u <service> --since '<start>' --until '<end>' --no-pager`，将每次请求与上游拨号错误逐次对齐。客户端的connection reset只说明连接被关闭；若代理同刻记录上游TCP拨号超时，才定位到该上游链路，不归为GitHub限流或零搜索结果。
3. 核对服务切换和配置生效时间。恢复发生在采集之后时，不能用恢复后的成功推翻早先真实故障；没有历史路由证据，不推断当时主备为什么没接管。
4. 分开做当前代理与显式直连对照：curl代理请求用`-x`，直连用`--noproxy '*'`；仅省略代理参数仍可能继承环境变量。记录目标HTTP响应，再验证真实查询和候选质量。
5. 将网络故障与查询编码、分类、门槛缺失分别列出证据；网络通不代表搜索正确，TCP超时也不能证明上游永久失效或遭封禁。保留历史失败事实，不拿今天候选回填成当日采集。

## 自动恢复的实施与验收
先画清正常采集、失败重试、内容接管三个入口的输入、输出文件和退出码，再改接线；磁盘状态机测试通过不代表调用方理解相同的成功语义。以下是验收要求，不代表整条自动恢复已完成。
- 查实际入口、任务enabled状态和执行顺序后复用现有调度；配置存在或通用站点健康不等于GitHub域名切换演练通过，不为排查切断生产代理。
- 分开网络、认证、限流、真空结果与质量淘汰；仅网络证据支持链路恢复动作，限流不得触发换节点。持久状态记录日期、尝试预算、下一真实执行窗口及失败证据，不能预约不存在的后续调度。
- 看门狗只处理已有且到期的失败状态；无状态或当日已成功时不无故重采。先验证并复用当日正常结果；临时文件丢失可从持久证据恢复，但不得替换已经发布的当日选项。
- 保留原采集入口的认证来源契约，不假定定时任务继承交互终端凭据；复用既有安全取凭据函数，不打印凭据。组件配置注入任务关联，不写死问题单标识。
- 对临时目录和进程锁实跑初次成功、失败后恢复、重复运行、并发、崩溃预占、跨日隔离、掉临时文件恢复及安装失败回滚；内存状态机测试不能代替磁盘与入口接线测试。
- 用安装后的真实入口验证退出码：正常初采成功返回原调用方认可的成功码，不能因为下游未ack而把正常采集误报失败；仅补偿产物使用独立pending接管状态。候选初采失败时写本日显式失败结果，避免生成器继续读取上日临时文件；已有当日正式推荐则保留原选择，不自动替换。
- 部署前以源文件hash校验和备份防覆盖，安装器先执行真实磁盘集成测试，再更新全部入口；验证捕获异常时能回滚，不把多文件替换称为断电事务。部署后在已有正式日报的环境实跑无操作路径，确认不调用采集API、候选内容不变。
- 将候选与待接管证据放在同一原子持久状态中，再按条件恢复临时物化文件；无日期的历史库只提供去重事实，不能为了接纳今日结果擅自删除历史项或推定其推荐日期。归属不明时保留阻塞证据，不重复采集。
- 候选恢复必须有明确后续消费者接管日报、摘要、结构化数据、飞书、IMA及站点补偿；只落pending文件却无人消费不是闭环。逐目标回读与去重，补采成功不自动宣称多渠道已恢复。

## 搜索传参
把查询词与限定符作为独立参数传入gh，避免整串含冒号查询被CLI自动加引号、把关键词吞进限定符：

```python
cmd = ['gh', 'search', 'repos', *shlex.split(query),
       '--sort', 'stars', '--limit', str(limit),
       '--json', 'fullName,description,stargazersCount,url,createdAt']
```

query由受控词表构造；如需精确短语，显式保留短语引号。不要通过shell拼接执行。查询星数很高却总返回同一批泛项目时，核对实际请求q，而不是据返回成功认定查询有效。

## 门槛与搜索覆盖
星数判定复用候选脚本STAR_POLICY/eligible_repo：优先万星成熟仓；兜底至少500星且API创建时间在180天内。低星缺创建时间拒绝，异常星数类型拒绝。查询条件与入选过滤两层都执行；修相关性、补数量不得移除门槛。

在有限查询预算内先轮换不同关键词检索成熟仓，再保留新仓兜底名额；不要让第一个关键词的多种日期fallback耗光预算。候选不足继续调整关键词而非降低质量、重复历史或凭印象补项目。

## 功能分类
以实际产品功能判断归属，MCP/API/LLM等接入标签不能压过明确的视频编辑、设计、企业检索功能。无关项目返回无分类，不能给技术赛道固定加分而把所有内容吸进去。关键词匹配需有词边界，避免api命中capital、rag命中storage；边界测试之外仍需对入选候选做人类语义复核。

## 双层验证
- 离线：低于500拒绝；500且180天内接受/超期拒绝；万星老仓接受；布尔/字符串/浮点星数拒绝；缺日期的新仓拒绝；历史/跨赛道/大小写重复拒绝。
- 发布校验：实际违规报告应报错，合格三赛道应通过；精确星数与当日候选一致，不允许写“星数不高但结构完整”豁免。
- 真实采集：逐赛道至少有一个合格候选；验证当前日期、来源元数据、历史去重与跨赛道去重，不能只看总数。

## 入库质量
飞书为历史推荐权威源，本地recommended-repos.json是重建的缓存，采集还与近期正式报告取并集去重；不要沿用“历史库已废弃”旧结论。

描述与推荐理由分别写真实功能、读者用途，不用模板泛称“AI相关项目”，理由不重复星数。Stars/Forks传整数。类型分类优先具体功能，防止learning、collection等泛词误判书籍。写入后按目标记录回读，不把成功响应或本地缓存当外部写入证据。
