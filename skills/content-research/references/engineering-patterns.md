# 单点收拢架构（Single Source of Truth Pattern）

## 根因

LLM 在面对「禁止 X」「必须按 Y 校验」类软规则时，会在**多处副本**中漂移——不是因为不理解，而是因为：

1. **每处副本自己维护一份规则** — N 处副本就有 N 份可能错位的版本
2. **更新必须 N 处同步** — 漏一处就会出现「旧版本 + 新版本」并存
3. **每处副本都有自己的注意力权重** — LLM 加载时只读其中一处，另外几处等同失效
4. **规则越复杂，复制保真度越低** — 反例/正例/自检清单容易被截断或改写

实证（2026-08-21 content-research 共识/分歧硬约束）：
- 「共识/分歧段落禁止出现具名事件/品牌/数字」这条规则原本被复制到 4 处——SKILL.md 完整版模板上方（~250 字）+ SKILL.md 精简版模板上方（重复）+ references/output-template.md（~350 字）+ cron jobs.json 该任务 prompt（1064 字）
- 4 处副本共 ~1700 字，且每处措辞/反例细节略有差异
- 用户原话：「我希望用可复用组件、可复用模块的思维，确保只有一份模板文件、一份skill入口、一份cron Prompt、一份脚本，避免多处重复」

## 正确架构：1 权威 + 1 脚本 + N 处引用

任何「禁止 X」「必须按 Y 校验」类硬规则，落地时**必须同时具备**：

### 1️⃣ 一份权威定义文件

放在 `references/<topic>-rules.md`（YAML frontmatter + markdown body），**唯一**包含
- 反例清单（≥ 3 条，取自真实违规输出原文）
- 正例清单（≥ 1 条，同样信息量的合规写法）
- 自检步骤清单
- 退出码语义

**禁止**在别处复制这段内容——别处只能「引用文件名 + 调脚本」。

### 2️⃣ 一份自动化校验脚本

放在 `scripts/<topic>_check.py`，**唯一**承担：
- 读取报告/产物文件
- 应用反例关键词 + 正则模式
- 应用自检逻辑（字数、格式、引用事件数等）
- 退出码语义：`0`=合规 / `1`=违规 / `2`=文件错误

脚本可挂 cron 末尾、pre-commit hook、手动验收、LLM 自检。

### 3️⃣ N 处轻量引用

所有需要执行该规则的地方（SKILL.md / references 子模板 / cron prompt / 报告生成脚本）**只引用**：

```markdown
> 🔴 **<规则名>硬约束**已在 `references/<topic>-rules.md` 单点定义。
> 本模板**禁止复制**规则内容——只引用文件名 + 调用校验脚本：
> - 详细规则见：`references/<topic>-rules.md`
> - 报告生成/交付前必跑：`python3 scripts/<topic>_check.py --report <path>`
> - 校验脚本退出码 `0` = 合规可交付，`1` = 命中反例必须重写，`2` = 文件错误
```

不要在 SKILL.md / cron prompt 里再粘贴反例清单——那叫「复制副本」，不是「引用」。

## 重构 5 步法

当发现某条规则已经在 N 处副本散落时，按这 5 步收敛：

1. **建权威文件** — `references/<topic>-rules.md`，把 N 处副本合并去重，作为唯一来源
2. **建校验脚本** — `scripts/<topic>_check.py`，把自检逻辑做成可执行代码（含反例正则 + 退出码语义）
3. **删 SKILL.md 副本** — 把 SKILL.md 里所有规则副本替换成「引用权威文件 + 调脚本」（用 patch 工具一次性 replace_all）
4. **删子模板副本** — `references/output-template.md` 等子模板同样替换
5. **删 cron prompt 副本** — `cron jobs.json` 里 prompt 的硬约束段替换成「引用权威文件 + 调脚本」命令

**实测收益**（2026-08-21 content-research）：
- SKILL.md：-1064 字（2 处副本换 2 处引用）
- references/output-template.md：-350 字
- cron jobs.json：2600 → 1951 字（节省 25%）
- 校验脚本能硬阻断 21 个反例关键词 + 引用事件数 + 实词数

## 校验脚本设计要点

设计 `scripts/<topic>_check.py` 时必须做到：

- **退出码语义明确**（0/1/2）—— cron 流水线可接 stderr 决策重试/告警
- **支持 `--json` 输出** —— 下游 LLM 可解析违规详情
- **支持 `--report <path>` 参数** —— 可检查任意报告文件，不只是默认当天
- **反例用正则而非精确字符串** —— "Stripe" 命中变体 "Stripe 70亿美元" / "Stripe 据传" 等
- **中文标点 + Markdown 符号** 在计数/匹配前先剥掉（避免加粗符号干扰）
- **违规时打印具体命中位置** —— 不要只说"违规"，要说"第 X 段命中 Y 模式"便于修复

## 适用范围（不限于共识/分歧）

任何「禁止 X」「必须按 Y 校验」类规则都该用这套架构：

- 内容质量硬约束（共识/分歧、推荐阅读、GitHub 推荐选取）
- 格式硬约束（字数、Markdown 符号、分行）
- 必跑流程（IMA 同步、GitHub 历史去重、报告推送）
- 安全/合规约束（禁止上传某个 key、必须用某 API）

每发现一类「禁止 X」规则在多处副本存在，就按 5 步法收敛到一处。

## 与 anti-drift-rule-pattern 的关系

- **anti-drift-rule-pattern**（v7.12）：解决「禁止 X 类软规则被 LLM 漂移违背」—— 四件套（结构隔离 + 反例 + 正例 + 自检 + 硬失败判定）
- **single-source-of-truth-pattern**（本文件）：解决「同一条规则被复制到 N 处副本，N 处漂移不同步」—— 1 权威 + 1 脚本 + N 引用

两者是互补的：单点收拢保证规则定义只活在一处；anti-drift 保证那「一处」内的规则足够强、不会被 LLM 默默违背。

## 验收清单

新增任何「禁止 X」类规则时，逐项打勾：

- [ ] **references/<topic>-rules.md** 权威文件已建（含反例 + 正例 + 自检 + 退出码）
- [ ] **scripts/<topic>_check.py** 校验脚本已建（支持 `--report` + `--json`）
- [ ] **SKILL.md** 里所有副本已删，换成引用块
- [ ] **references/ 子模板** 里所有副本已删，换成引用块
- [ ] **cron prompt** 里所有副本已删，换成引用块 + 调脚本命令
- [ ] 实测：合规报告 exit 0，违规报告 exit 1
- [ ] fact_store 永久记忆已沉淀（避免 memory 字限丢失）

# 防规则漂移模式（Anti-Drift Rule Pattern）

## 根因

LLM 面对「禁止 X」「不要做 X」「禁止 Y 现象」这类软规则时，会在长 context 或多段落任务中**静默违背**——不是因为不理解规则，而是因为：

1. **没有结构性隔离** — 「禁止 X」和「允许 Y」在同一段落里共存，模型的注意力被允许的样式吸走
2. **没有反例锚点** — 模型不知道「违背」具体长什么样，模板里只有抽象描述
3. **没有自检命令** — 生成后没有一个可执行的「我有没有违背规则」的检查流程
4. **没有硬失败判定** — 软规则配软判定（"尽量避免"），违背了也只是轻微扣分，不会触发重写

实证：2026-08-21 共识/分歧段落，软规则「禁止复述引用事件」被 LLM 在 4 个不同位置上反复违背——Ramp Router、Stripe、OpenRouter、阿里 AI ARR、WRC 2026、量子位等具名事件都漏到了「核心结论+扩展说明」段落里。

## 四件套升级方案

把任何「禁止 X」类软规则升级成下面四件套，**必须同时具备**才能真正阻断漂移：

### 1️⃣ 结构性隔离（Structure Isolation）

把「禁止区域」和「允许区域」在文档结构上**物理分开**，不要让它们在同一段落/同一缩进层级出现。

**反面**：模板里说「核心结论段落禁止出现具名事件，引用事件可以在最后列」，但都写在同一段，模型注意力分散。

**正面**：用空行 + 二级标题把段落切干净——
- 「核心结论+扩展说明」段落：纯机制层文字
- 「▸ 引用 N」段落：只在这里允许出现事件名/数字/品牌

### 2️⃣ 反例锚点（Anti-Examples）

从真实违规输出里**摘取原文**作为反例，明确列出「这种写法禁止出现」。反例越具体（带具体品牌名/数字/句式），锚定效果越强。

**模板**：
```
❌ 反例 1：[违规原文，包含具名事件/数字/品牌]
❌ 反例 2：[违规原文]
❌ 反例 3：[违规原文]
```

为什么「禁止罗列事件」不够 — 因为模型不知道「罗列」长什么样。给出「Ramp Router（降本 40%）、Stripe 收购 OpenRouter（溢价 5.4x）、阿里 AI ARR 破百亿——三方独立信号指向同一结论」这样的反例，模型立刻知道什么是被禁止的样式。

### 3️⃣ 正例锚点（Positive Examples）

同样的信息量，给出**符合规则**的写法。让模型看到「不是不让你说，是换一种说法」。

**模板**：
```
✅ 正例 1：[同样信息、合规写法]
✅ 正例 2：[同样信息、合规写法]
```

「AI 用得越深的企业，反而最先为成本管理付钱——卖水人比淘金者更早规模化」vs「Ramp Router（降本 40%）、Stripe 收购 OpenRouter（溢价 5.4x）、阿里 AI ARR 破百亿——三方独立信号指向同一结论」——两段话信息密度差不多，但前者是机制层结论，后者是事件罗列。

### 4️⃣ 自检命令 + 硬失败判定（Self-Check + Hard Failure）

给一个**可执行的**自检步骤，并明确「自检失败 = 整篇不合格 = 必须重写」，而不是「尽量避免」。

**模板**：
```
生成后必须执行：
1. 把核心结论+扩展说明单独复制到新文档
2. 把所有「引用事件」行全删掉
3. 如果删完后段落失去信息量或读不懂 → 说明还在罗列事件，必须重写

硬判定：如果上面反例任一条仍出现在生成结果中，整篇报告视为不合格，必须重写该段落再交付。
```

## 适用范围（不止于共识/分歧）

这条模式适用于任何「禁止 X」类规则被反复违背的场景。常见触发点：

- **禁止重复/罗列**（事件、品牌、数字、链接）
- **禁止占位符**（省略号、TODO、URL 不完整）
- **禁止翻译腔/AI 腔**（具体词汇、句式）
- **禁止超长/超短**（段落字数、行数）
- **禁止情绪化/营销词**（夸张、煽动）
- **禁止泄露内部信息**（公司名、未公开数据）

每出现一次「你又 X 了」的反馈，就把对应规则升级成四件套。

## 验收清单

新增或修改任何「禁止 X」类规则时，逐项打勾：

- [ ] 结构性隔离 — 「禁止区域」和「允许区域」在文档结构上分开
- [ ] 反例锚点 ≥ 3 条 — 取自真实违规输出原文
- [ ] 正例锚点 ≥ 1 条 — 同样信息量、合规写法
- [ ] 自检命令可执行 — 不是「请检查」而是「执行 X 步骤」
- [ ] 硬失败判定 — 「不合格 = 必须重写」而非「尽量避免」
- [ ] 嵌入 cron prompt / 生成模板 — 软规则只在 SKILL.md 写了没用，必须同步到 LLM 实际加载的 prompt
- [ ] 自检脚本化（可选但推荐） — `scripts/<rule>_check.py`，可挂 cron 末尾 / pre-commit / 手动验收

# 产物异常取证 + 校验器硬化（谁写的这个问题？）

发现简报出现不该有的内容（多余条目、过程说明、格式混排）时，**先判定责任方，再动手**——改错地方会浪费一整轮。

## 第 1 步：先搜规则与脚本，判定「脚本产出」还是「模型自造」

grep 全链路：`scripts/` + `references/` + `cron/jobs.json` 的 prompt + 校验器。
- **命中** → 规则/脚本问题，改那一处
- **零命中** → 该措辞是**模型自己造的**，不要改脚本，去补硬校验（第 3 步）

⚠️ **grep 陷阱**：会话库里工具调用参数是以 JSON 存储的，**非 ASCII 字符会被转义成 `\uXXXX`**——直接 `LIKE '%中文短语%'` 搜不到，会误判成「不存在」。可靠做法：用同一段 payload 里的 **ASCII 子串**（产品名、英文词）定位，或按转义形式搜。

## 第 2 步：定位生成现场（state.db 取证）

```sql
-- 会话名格式：cron_<job_id>_<YYYYMMDD>_<HHMMSS>
SELECT id, role, tool_name, length(content) FROM messages WHERE session_id = 'cron_<jobid>_<date>_<time>' ORDER BY id;
SELECT tool_calls FROM messages WHERE id = <命中行的 id>;   -- 真正写入的内容在这里
```

- 助手的文本 content 可能只有一句「现在生成完整版…」（几十字），**实际写盘内容在 `tool_calls` 的 `write_file.content` 参数里**——不要在 content 列搜不到就下结论
- 用 `sqlite3.connect('file:...state.db?mode=ro', uri=True)` 只读打开，避免干扰运行中的 agent
- 同一次运行里往往能同时看到**正确的那一版**（如微信摘要版 3 条全对）→ 说明是单版生成漂移，不是数据缺失

## 第 3 步：把异常写成硬校验，并用「坏样本回放」证明它会红

1. 在 `daily_briefing_check.py` 加硬校验（条数精确、禁词、序号混排）——规则必须有执行层，写在 prose 里等于没写
2. **坏样本回放**：把事故原文还原到临时文件 → `importlib` 加载校验器直接调 `check_file(path, today)` → **期望命中 N 条具体报错**
3. 再用修复后的正式产物跑一遍 → **期望 0 报错**
4. 回放通过后才改内容，并同步三处：权威 references 规则 + 校验脚本 + SKILL.md 铁律

> 只跑「修复后是绿的」不算验证——**没有坏样本命中的证据，就不知道这道闸门会不会真的拦**。
