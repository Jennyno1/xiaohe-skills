# 信息源健康监控（2026-09-23 建）

## 为什么要有它

预采集脚本（`~/.hermes/scripts/collect_daily_feeds.sh`）只打印**素材池总条数**，单个源成败完全不体现：
日志里全是「英文 RSS 拉取完成」这类不区分成败的行，而简报输出规范里也没有异常栏。
→ 结果：源静默挂掉 → 素材变少 → 简报照常生成，**用户与生成侧都不知道少了几个源**。

实测（2026-09-23）：20 个源里 5 个抓取失败（阿里云 feed 地址失效、36氪热榜/虎嗅被 RSSHub 超时砍成 0 字节、
VentureBeat 429、OpenAI 偶发），而没有任何提醒。

## 三层防护

| 层 | 位置 | 作用 |
|---|---|---|
| 检查器 | `~/.hermes/scripts/check_source_health.py` | 判定每个源状态；支持 `--json` / `--alert` / `--history N`；退出码 0/1/2 |
| 告警任务 | cron `9c5f368439ac`（每日 06:30，no_agent，deliver=all） | 只在有抓取失败时推一行；正常静默 |
| 生成侧条款 | `references/daily-briefing-rules.md` 第九节 + 日报 cron prompt 7.5 条 | 失败 ≥2 源或素材池 <30 条 → 微信摘要末尾必须追加 `⚠️ 源异常：…` |

## 判据（关键：别把「无新条目」当故障）

- **抓取失败**（必报）：该源 0 条产出，且 feed 文件缺失 / <200B / 解析不了（HTML 错误页、429 页）。
- **无新条目**（不报）：feed 抓到了、窗口内确实没新内容（例：NVIDIA 官方博客最新一篇在 7 月）。
  慢更的官方博客经常这样，报出来只会造成告警疲劳。

源清单与 feed 路径映射写在 `check_source_health.py` 的 `SOURCES`（20 条，含 layer 标签）。
**新增/更换源时同步改这里**，否则新源永远处于「不监控」状态。

## 换源/修源三招（2026-09-23 实装）

源挂了先分类，再选招式：

| 症状 | 招式 | 实例 |
|---|---|---|
| feed 地址失效（返回 HTML / 404） | **列表页转 RSS**：写个抓取器把服务端渲染的列表页转成 RSS 落到原文件路径，解析层零改动 | `fetch_alibabacloud_blog.py`（阿里云 /blog/feed 失效） |
| curl 被 Cloudflare 拦（429，直连/代理/带完整头都没用） | **浏览器兜底**：`fetch_via_browser.py <url> --out <file>`（真浏览器指纹能过；**必须取 response.body() 原始字节**，`page.content()` 拿到的是包了一层的 HTML） | VentureBeat 的 RSS |
| 偶发网络失败 / 冷启动超时 | **补抓两轮**：先 curl 重试（45s），仍失败再浏览器兜底；只对 <200B 的文件触发 | 采集脚本英文源与 RSSHub 源均已有 |

判断该不该换源的前提：**先确认源本身还活着**（例：阿里云博客列表页每天都有新文，只是 feed 死了——那就是修不是删）。

## 坑

- 🔴 **判定 feed 文件要整份解析**：为省内存截断到前 200KB 会把合法 XML 判成「坏文件」（NVIDIA 就踩过）。
- 🔴 **RSSHub 路由超时要给够**：热榜/虎嗅的响应 160KB~640KB，原 `--max-time 10` 会砍成 0 字节文件；
  已改 30s + 失败补抓一轮。
- 🔴 **no_agent 告警脚本必须 exit 0**：非零退出会额外触发一条「执行失败」告警，与自己的告警行重复。
- **探活不等于端到端**：`curl` 拿到 200 不代表解析后有素材——所以判据落在「素材池里有没有这个源」，
  再回头用 feed 文件状态区分是抓取问题还是无新条目。
- **浏览器兜底要指定带 playwright 的解释器**：`$HOME/.hermes/hermes-agent/venv/bin/python`（cron 环境 PATH 不保证）。
- **feed 能抓 ≠ 内容新鲜**：VentureBeat 的 feed 能取到但最新一条停在 8/27，属于站点侧 feed 停更；
  这种情况健康检查会归为「无新条目」而不报错，需人工定期看是否要换源。

## 换源/加源的「五处同步」清单（漏一处就静默失效）

换一个源不是只改一行 curl——必须同批改完，否则新源不会进素材池，而且**不会报错**：

| # | 位置 | 漏改的后果 |
|---|---|---|
| 1 | `~/.hermes/scripts/collect_daily_feeds.sh` 的抓取行（放进对应的 `wait` 分组） | 文件根本没被抓取 |
| 2 | 同一脚本的**补抓列表**（`for pair in "文件:URL"`） | 偶发失败时不会被重试 / 浏览器兜底 |
| 3 | `scripts/parse_all_feeds.py` 的源 spec 列表 + `SOURCE_TYPE_MAP` | 文件拉到了但**永远不进素材池**（最隐蔽的一处） |
| 4 | `~/.hermes/scripts/check_source_health.py` 的 `SOURCES` | 新源处于「不监控」状态，挂了不告警（**减源时反过来：留着旧条目会天天误报**） |
| 5 | `references/{sources-catalog,execution-pipeline,ad-hoc-flow}.md` 的源清单与命令示例 | 文档与产线漂移，下次按旧文档操作 |

顺手 `rm` 掉被替换源的旧 `/tmp` feed 文件——残留文件会让健康检查把已退场的源算成「有产出」。

## 端到端验证配方（对付「今天已生成就跳过」的脚本）

`collect_daily_feeds.sh` 开头有 FRESH 早退（当天报告已存在就 `exit 0`），直接跑等于什么都没测。
配方：复制到 `/tmp/collect_test.sh`，**只改测试副本**——把 FRESH 分支里的 `exit 0` 去掉（改行 log），然后：

```bash
timeout 580 bash /tmp/collect_test.sh 2>&1 | grep -E "补抓|素材池 [0-9]|抓取失败（|❌"
```

生产脚本与当天报告都不动，但会重建素材池（顺带把当天缺的源补回来）。
判据：`抓取失败 0 个` + 目标源出现在 `source_counts` 里。
收尾 `rm /tmp/collect_test.sh`，别让它成为下周有人误跑的第二个采集入口。

## 改采集脚本的坑

- 🔴 **行连续列表（`\` 续行）要整块替换**：只 patch 其中一行会丢掉该行的续行符，把两条合并成一个畸形条目；
  `bash -n` 照样通过，运行时那条 URL 变成垃圾字符串 → **静默少抓一个源**。改完一律回改动处肉眼确认 `\` 还在。
